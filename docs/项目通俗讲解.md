# 我的 Web 服务器项目 · 大白话版

> 这份文档不讲术语，用生活中的比喻把整个项目讲明白。看完你能回答：这个项目是什么、它怎么工作、为什么要写这么复杂、那些 bug 都是怎么回事。

---

## 一、这个项目到底是个啥？

你用浏览器打开任何一个网站，本质上都是在做一件事：

> **你（浏览器）："喂，把首页给我看看。"**
> **网站的电脑（服务器）："好，首页文件在这儿，拿好。"**

服务器就是那台 24 小时不关机、专门负责"接电话、发文件"的电脑。这个项目，就是我**从零手写了一个这样的服务器程序**，没有用任何现成框架，全部用 C 语言直接操作操作系统。

光有服务器还看不出效果，所以我还给它配了个"小花仙"动漫主题的网站（首页、精灵王图鉴、404 页面）。服务器跑起来后，浏览器访问它，就能看到这些网页。

**为什么要手写而不是用现成的？** 因为现成的框架（Nginx、Apache）像一辆造好的车，你会开就行；而手写一遍，等于自己把发动机拆了再装回去——面试时别人问你"发动机怎么转的"，你是真懂，不是只会踩油门。

## 二、它是怎么工作的？（餐厅比喻）

把服务器想象成一家**餐厅**，来吃饭的客人就是浏览器的请求。

### v1 版本：每来一位客人，招一个服务员（每连接一线程）

最早的版本逻辑很简单：

1. 门口站个**大堂经理**（主程序），客人一进门就招呼；
2. **每来一位客人，当场招一个全职服务员**（创建一个线程），专门服务这桌；
3. 客人吃完走人，服务员**当场辞退**（线程销毁）。

客人少的时候没问题。但饭点来了 200 个客人呢？餐厅要在几秒钟内招 200 个服务员，他们在大厅里挤来挤去抢着用厨房（CPU），互相撞、互相等，有的客人等了 1.6 秒还没上菜（超时）。**招人、辞人、人挤人，全是开销。**

压测数据证明了这点：v1 每秒只能处理 5897 个请求，而且延迟忽高忽低，标准差 110 毫秒，还有 11 次超时。

### v2 版本：固定服务员团队 + 智能叫号（epoll + 线程池）

升级版改成了高级餐厅的运作方式：

1. **大堂经理**（主线程）不再亲自服务客人，他只干一件事：盯着整个大厅，**谁举手了（有请求来了），他就记下来**。这个"一眼看全场谁有事"的能力，就是 `epoll`——操作系统提供的高效"叫号器"，能同时盯着几万个客人而不累。
2. 餐厅养着**固定数量的服务员**（线程池，比如 4 个），不随客人多少变化。客人再多，也是这 4 个人轮流转，绝不现场招人。
3. 大堂经理看到客人举手，就把这桌**派给一个空闲服务员**；服务员忙完一桌，回到池子等下一单。

这样客人从 1 桌涨到 1 万桌，服务员团队始终是 4 个人，没有招人辞人的开销，也没人挤人。

**效果：同样的短连接测试，每秒处理 21568 个请求（3.7 倍），延迟从 21 毫秒降到 4 毫秒，而且零错误。**

### 还有个省钱技巧：别让客人吃完就走（Keep-Alive 长连接）

客人和餐厅之间每建立一次"服务关系"，都要先敲门、握手、寒暄（TCP 三次握手），吃完了还要道别、关门（四次挥手），这些都花时间。

v1 时代是"客人吃完立刻送客"（短连接）。v2 发现：很多客人吃完一道菜还想点下一道（一个网页往往要连续请求 HTML、图片、CSS 好几个文件），**与其送走再重新敲门，不如让客人先坐着别走，15 秒内有事随时招呼**（这就是 Keep-Alive 长连接）。

就这一个改动，每秒请求数又从 2.1 万涨到了 **5 万**。

## 三、各个"部门"都是干嘛的？

项目代码放在 `src/` 目录，拆成了几个文件，每个就像餐厅的一个部门：

| 文件 | 比喻 | 大白话解释 |
|------|------|-----------|
| `webserver.c` | 大堂经理 + 总指挥 | 主程序：开门营业、盯着全场、分派任务、给客人上菜 |
| `threadpool.c/.h` | 服务员团队管理 | 线程池：固定招一批服务员，任务来了从池子里领人，忙完归还 |
| `http_parser.c/.h` | 听懂客人点菜的翻译 | 浏览器说的是"HTTP 方言"（`GET /index.html HTTP/1.1`），这个模块负责听懂客人要哪个文件、还有没有附加要求。还负责安检：客人要是说"我要去后厨外面的仓库看看"（路径里有 `..`，想偷看系统文件），直接拒绝 |
| `timer_wheel.c/.h` | 翻台计时器 | 客人坐了 15 秒什么都不点（长连接空闲），自动收盘送客，防止座位被占满。用的是"时间轮"结构，可以理解成一个秒针转盘，指针每转一格扫一遍谁该走了 |
| `log.c/.h` | 餐厅流水账本 | 每个客人几点来的、点了什么、有没有出状况，都记账。专门请了个"记账员"（后台线程）批量写本子，不让服务员因为记账耽误上菜 |
| `legacy/myweb_v1_thread.c` | 旧版餐厅（留档） | v1 的代码特意保留下来，用来和 v2 对比、压测，证明新架构快在哪 |

还有些"规矩"散落在总指挥那里：

- **`sendfile` 零拷贝**：给客人上菜时，菜（文件内容）不用从厨房端到前台再端上桌，直接从厨房窗口滑到客人桌上（数据不经过应用程序内存，由操作系统内核直接搬运），省一道手。
- **`TCP_NODELAY`**：后面讲 bug 时细说，是个"别磨蹭，有话立刻说"的开关。

## 四、踩过的那些坑（这个项目最值钱的部分）

代码写完不代表能跑对。压测（用 `wrk` 工具模拟几万个客人同时上门）时，问题一个接一个炸出来。**这些坑比代码本身更值得讲**，因为每一个都是真实餐厅会遇到的管理事故。

### 坑 1："厨房忙不过来"被误判成"餐厅着火了"

**事故现场**：第一次压测，每秒只服务了 3.47 个客人，几万客人被服务员当场赶走（27 万个错误）。

**怎么回事**：服务员给客人上菜用的是"传送带"（非阻塞网络发送）。传送带偶尔会堆满，这时传送带会喊一句"等一下，满了，一会儿再送"（系统返回 `EAGAIN`）。**这是正常现象**，正确做法是稍等片刻、传送带空了继续送。

但我写的服务员一听"等一下"，以为出了大事，直接把客人推出门、收摊走人。客人当然一脸懵（连接被重置）。

**怎么修的**：教服务员听懂这句话——"满了"不等于"坏了"，把这盘菜记在账上（保存发送进度），等传送带空了（系统通知"可以写了"）再接着送，从哪儿断的从哪儿继续。

### 坑 2：翻台计时器把正在吃饭的客人赶跑了

**事故现场**：程序直接崩溃（段错误），像餐厅经理当场晕倒。

**怎么回事**：这是个"两个员工同时管一张桌子"的事故。服务员正在给某桌客人上菜，而翻台计时器的秒针正好扫到这桌、以为客人走了，冲过去把桌子收了、椅子扔了（关闭连接、释放内存）。服务员端着菜回来一看：桌子呢？？一伸手就抓空了（操作了已经被释放的内存，程序崩溃）。

**怎么修的**：立规矩——**大堂经理在派单的那一刻，就先把这桌的计时器摘了**，服务员服务期间谁也不许碰这桌的计时器。服务员忙完重新放回去。从流程上保证"一张桌子同一时刻只有一个人管"。

### 坑 3：一张桌子挂了两个计时器

**事故现场**：坑 2 修完还是偶尔崩溃。

**怎么回事**：服务员忙完一桌要做两个动作：① 重新举手叫号（继续盯着这桌）② 挂上新计时器。原来的顺序是先叫号、后挂计时器。结果在两步之间，大堂经理已经看到这桌客人又举手了，冲过去摘计时器——**可新计时器还没挂上去呢，摘了个空气**。之后服务员挂上计时器 A，下次忙完又挂一个计时器 B，一张桌子挂了俩表。15 秒后 A 表响了，把正被别的服务员服务的桌子又收了。

**怎么修的**：调换顺序，**先挂计时器、再举手叫号**。保证"经理可能看到客人举手"的那一刻，计时器一定已经挂好了。另外还在计时器本身上了双保险：挂新表之前先检查有没有旧表，有就扔掉——一张桌子永远只允许有一个计时器。

### 坑 4：计时器疯了——15 秒的表 1 毫秒就响

**事故现场**：不崩溃了，但还有 9 万多客人被错误赶走。更怪的是，有一次成绩看着特别好（1.8 万 QPS）。

**怎么回事**：这是全篇最隐蔽的坑。翻台计时器的秒针设计上是**每秒"滴答"走一格**，靠"大堂经理每秒钟抬头看一次钟"来驱动。

但我写错了：经理**每处理完一批客人就滴答一下**。没客人时经理每秒处理 1 批，表走得准；可压测时客人潮涌进来，经理**每秒要处理上万批**——秒针于是每秒狂转上万格，设定"15 秒后响"的表，**几毫秒就响了**。刚上完一道菜、等客人点下一道的桌子（长连接两次请求之间有零点几秒空闲），被瞬间判定"超时"收掉。

那次"1.8 万 QPS 的好成绩"也是假象：桌子被疯狂收掉、客人被赶走重排，看着热闹，其实全在折腾。

**怎么修的**：经理不能再按"我忙了几轮"来计时，改成**看真实的时钟**（操作系统的单调时钟），无论忙闲，实打实过了 1 秒才让秒针走一格。

**教训**：时间只能用时钟量，不能用"我干了多少活"量。

### 坑 5：厨师和传菜员互相等，每桌干等 40 毫秒

**事故现场**：错误清零了，但新现象很怪：每桌客人都要等 **43 毫秒**才上菜，误差极小（标准差才 3 毫秒），而且奇怪的是——**让客人吃完就走（短连接）反而比让客人坐着等（长连接）更快**，这不合常理。

**怎么回事**：延迟稳稳地卡在一个固定值上，说明不是"忙不过来排队"，而是"每次都在等某个固定的东西"。这是网络协议里的著名死锁：

- 厨房有个省电规矩（Nagle 算法）：小菜碟（零碎的小数据包）先攒着，等客人那边回个话（ACK 确认）再一起端，少跑几趟；
- 客人那边也有个懒规矩（延迟确认）：收到小菜不着急回话，**最多攒 40 毫秒**再回。

于是：厨房等客人回话 → 客人等 40 毫秒才回话 → 每桌白白干等 40 毫秒。
而短连接客人起身离店时会"喊一嗓子"（关闭连接的信号）顺带把话递过去，反而绕开了这个等待，所以看起来更快。

**怎么修的**：给所有桌子装个开关（`TCP_NODELAY`）："菜好了立刻上，别攒着等回话。"这也是 Nginx 等专业服务器的默认做法。

**效果**：平均延迟从 43.59 毫秒掉到 **3.63 毫秒**，QPS 从 4540 冲到 **5 万**，长连接也重新变回比短连接快——世界恢复正常。

## 五、最终成绩单

同样的机器、同样的 10KB 网页、同样用 wrk 模拟客人：

| 方案 | 每秒接待客人（QPS） | 平均等待时间 | 出状况 |
|------|------|------|------|
| v1 每客招一服务员 | 5,897 | 21 毫秒 | 11 桌超时，等待时间忽长忽短 |
| v2 固定团队 · 吃完就走 | 21,568 | 4.1 毫秒 | 0 |
| v2 固定团队 · 客人留座 | **50,141** | 3.6 毫秒 | 0 |

从每秒 3.47 个请求、几万错误，到每秒 5 万个请求、零错误，中间修了 5 个真实的并发问题。

## 六、怎么自己跑起来？

```bash
# 1. 编译（需要 Linux 环境）
make

# 2. 启动服务器（8080 端口，4 个服务员）
./myweb -p 8080 -t 4

# 3. 浏览器打开
#    http://127.0.0.1:8080        → 小花仙首页
#    http://127.0.0.1:8080/随便写  → 自定义 404 页面

# 4. 压测（自动起服务、跑测试、出报告）
./benchmark.sh 8080 4
```

## 七、如果面试被问到，三句话讲清楚这个项目

1. **我用 C 从零写了个 HTTP 服务器**，主线程用 epoll 统一监听事件，固定大小的线程池处理请求，配合时间轮管理长连接超时、sendfile 零拷贝发文件。
2. **我用 wrk 做压测驱动优化**：从每连接一个线程的 v1 演进到 epoll Reactor 的 v2，短连接 QPS 提升 3.7 倍，Keep-Alive 下达到 5 万 QPS、零错误。
3. **过程中排查了几个真实的并发问题**：非阻塞发送的 EAGAIN 处理、定时器与工作线程的竞态、时间轮被事件循环频率错误驱动导致飞转、以及 Nagle 与延迟确认互相等待造成的 40 毫秒固定延迟。

（详细技术版见 `docs/performance-notes.md`，对外展示版见 `README.md`。）
