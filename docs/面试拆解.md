## 三、网络编程基础拷打

### Q1：讲讲 TCP 三次握手，为什么是三次不是两次？

**大白话**：你和别人打电话——
- 你："喂，能听到吗？"（SYN）
- 对方："能听到，你能听到我吗？"（SYN+ACK）
- 你："能听到，那我们开始聊吧。"（ACK）

三次握手保证双方都能确认对方的收发能力。两次的话，服务端发了 SYN+ACK 后不知道客户端有没有收到，万一客户端之前的旧请求延迟到达，服务端就会白建一个连接浪费资源。

**专业术语**：三次握手防止历史连接（旧 SYN）造成的无效连接。RFC 793 规定 TCP 连接建立需要 3-way handshake，核心目的是同步双方序列号（ISN）并防止旧的重复连接请求被误接受。

**和项目的关联**：你的服务器 `accept4()` 返回时，三次握手已完成，拿到的是已建立的 TCP 连接 fd。

---

### Q2：四次挥手为什么是四次？为什么有 TIME_WAIT？

**大白话**：挂电话不是同时挂的——
- 你："我说完了，挂了啊"（FIN）
- 对方："好的我知道了"（ACK），然后对方可能还有话要说
- 对方："我也说完了，挂了"（FIN）
- 你："好的，再见"（ACK）

为什么你最后要等一下（TIME_WAIT）才真正挂？因为你的"再见"可能对方没收到，对方会重发"我也说完了"，你得留着等一会儿，万一对方没收到你的 ACK 就重发。

**专业术语**：四次挥手因为 TCP 是全双工的，每个方向的关闭需要独立进行（FIN + ACK）。TIME_WAIT 状态持续 2MSL（Maximum Segment Lifetime），作用有二：①确保最后一个 ACK 能到达对端，若对端未收到会重发 FIN；②让旧连接的报文段在网络中消亡，防止影响新连接。

**和项目的关联**：Keep-Alive 长连接避免频繁握手挥手，是 QPS 从 2.1 万涨到 5 万的关键。短连接每次请求都要握手+挥手，开销大。

---

### Q3：socket 编程的基本流程？

**大白话**：就像开一家店——
1. 拿营业执照（`socket()` 创建套接字）
2. 找个门面挂牌（`bind()` 绑定 IP+端口）
3. 开门等客（`listen()` 开始监听）
4. 客来了接客（`accept()` 接受连接）
5. 和客人聊天（`recv()/send()` 收发数据）
6. 关门（`close()` 关闭套接字）

客户端则是：`socket()` → `connect()` → `send()/recv()` → `close()`

**和项目的关联**：

```
服务器端流程（项目中的代码）：
  socket()  → create_listen_socket() 里的 socket(AF_INET, SOCK_STREAM|SOCK_NONBLOCK|SOCK_CLOEXEC, 0)
  bind()    → bind(lfd, ...)
  listen()  → listen(lfd, 1024)    // backlog=1024
  accept()  → accept4(lfd, ..., SOCK_NONBLOCK|SOCK_CLOEXEC)  // 主线程循环 accept
  recv()    → conn_worker() 里的 recv(fd, ctx->rbuf+ctx->rlen, ...)
  send()    → flush_response() 里的 send(ctx->fd, ctx->headbuf+ctx->headsent, ...)
  sendfile()→ flush_response() 里的 sendfile(ctx->fd, ctx->filefd, &off, ...)
  close()   → close_conn() 里的 close(ctx->fd)
```

### Q4：SOCK_NONBLOCK 和 SOCK_CLOEXEC 是什么意思？

**大白话**：
- `SOCK_NONBLOCK`：这个插座不会"卡住"。正常情况下 `recv()` 没数据时会一直等着（阻塞），设了这个标志后没数据就立刻返回说"现在没有"（非阻塞）。
- `SOCK_CLOEXEC`：防止"生孩子时泄密"。如果服务器用 `fork()` 创建子进程，子进程会继承所有打开的文件描述符。设了这个标志后，`exec()` 执行新程序时会自动关闭这个 fd，防止文件描述符泄漏。

**专业术语**：
- `SOCK_NONBLOCK`（Linux 2.6.27+）：等价于对返回的 fd 执行 `fcntl(fd, F_SETFL, O_NONBLOCK)`，原子地创建非阻塞套接字。
- `SOCK_CLOEXEC`：等价于 `fcntl(fd, F_SETFD, FD_CLOEXEC)`，在 `execve()` 时自动关闭该 fd，防止文件描述符泄漏到子进程中。原子操作避免了创建 fd 和设置标志之间的竞态窗口。

---

### Q5：accept 和 accept4 的区别？

**大白话**：`accept4` 就是 `accept` 的加强版，多了一个 flags 参数，可以在接收连接的同时一步到位地设置非阻塞和 CLOEXEC，省得再调一次 `fcntl`。

**专业术语**：`accept4()` 是 Linux 专有扩展（glibc 2.10+），相比 POSIX `accept()` 多一个 `flags` 参数，支持 `SOCK_NONBLOCK` 和 `SOCK_CLOEXEC`，避免了 accept 返回后再调两次 fcntl 的竞态窗口和额外系统调用开销。

## 四、epoll 与 I/O 多路复用拷打

### Q6：select / poll / epoll 的区别？为什么 epoll 最高效？

**大白话**：想象你是一个保安，要盯着 1000 扇门有没有人来——

| 方式 | 比喻 | 问题 |
|------|------|------|
| select | 每次都挨个问1000扇门"有人吗？"，问完发现只有2扇有人 | 每次都要遍历全部，而且最多只能盯1024扇（FD_SETSIZE限制） |
| poll | 和 select 差不多，但没有1024扇的限制 | 还是要遍历全部 |
| epoll | 装了个传感器，哪扇门有人了传感器自动告诉你 | 只需要处理真正有事件的门，O(就绪fd数) |

**专业术语**：

| 维度 | select | poll | epoll |
|------|--------|------|-------|
| 数据结构 | bitmap（1024限） | 动态数组 | 红黑树（注册）+ 就绪链表（返回） |
| 时间复杂度 | O(n) 遍历全部 | O(n) 遍历全部 | O(1) 只返回就绪的 |
| fd 上限 | FD_SETSIZE(1024) | 无限制 | 无限制（受系统 fd 上限） |
| fd 拷贝 | 每次调用都全量拷贝到内核 | 每次全量拷贝 | 只在 epoll_ctl 时拷贝一次 |
| 触发模式 | 只有 LT | 只有 LT | 支持 LT 和 ET |
| 适用场景 | 连接数少 | 连接数少 | 高并发（C10K+） |

**epoll 内核原理**：
- `epoll_create1()`：创建 epoll 实例，内核维护一棵红黑树（存放注册的 fd）和一个就绪链表
- `epoll_ctl(ADD/MOD/DEL)`：向红黑树插入/修改/删除 fd，并在内核中注册回调
- `epoll_wait()`：直接从就绪链表取数据，有事件则返回，无则阻塞
- 当 fd 上有数据到达时，内核通过回调将该 fd 加入就绪链表

### Q7：epoll 的 LT 和 ET 模式有什么区别？

**大白话**：
- **LT（水平触发）**：缓冲区里只要还有数据没读完，就一直提醒你"还有数据！"像个唠叨的闹钟，你不按掉它一直响。
- **ET（边沿触发）**：状态变化的瞬间提醒你一次"有新数据来了！"然后就不管了。你必须一次把所有数据读完，不然下次它不会再提醒你。

**专业术语**：
- **LT（Level Triggered，水平触发）**：只要 fd 的缓冲区中有可读/可写数据，`epoll_wait` 就会持续返回该事件。编程简单，不容易漏读，但可能频繁唤醒。
- **ET（Edge Triggered，边沿触发）**：只在 fd 状态变化（如从不可读到可读）时通知一次。要求使用非阻塞 I/O 并循环读取到 `EAGAIN`，否则可能遗漏数据。效率更高（减少 epoll_wait 返回次数），但编程复杂度高。

**和项目的关联**：项目用 **LT 模式**。
- 监听套接字用 LT：循环 `accept4` 到 EAGAIN，防止连接积压
- 连接套接字配合 `EPOLLONESHOT`：事件触发后自动 disarm，工作线程处理完再 MOD 重新挂回

**面试加分话术**："我选择 LT 而不是 ET，因为 LT 编程更简单、不容易漏读数据。配合 EPOLLONESHOT 可以达到类似 ET 的效果——事件触发后自动摘除，工作线程独占处理。nginx 早期也用 LT。"

---

### Q8：EPOLLONESHOT 是什么？为什么要用？

**大白话**：想象一桌客人按了服务铃（epoll 事件）。如果不设 ONESHOT，可能在服务员还没服务完时，铃又响了，另一个服务员也冲过去——两个服务员同时服务一桌，乱套了。设了 ONESHOT 后，铃响一次就自动关掉，服务员服务完后手动重新开铃。

**专业术语**：`EPOLLONESHOT` 让事件在触发后自动从 epoll 的关注列表中移除（disarm）。这样同一 fd 的事件不会被多个线程同时处理。工作线程处理完后需要调用 `epoll_ctl(MOD)` 重新注册事件。代价是每次需要重新武装，但保证了连接级的线程安全。

**不用 EPOLLONESHOT 会怎样**：主线程 epoll_wait 返回 fd 可读事件 → 投递给线程 A → 线程 A 还在 recv → 此时 fd 又可读（比如对端发了新数据）→ epoll_wait 又返回 → 投递给线程 B → 线程 A 和 B 同时操作同一 fd → 数据混乱/崩溃。

---

### Q9：epoll_wait 的 timeout 参数怎么用？

**大白话**：`epoll_wait` 最后一个参数是"等多久"。传 `-1` 就一直等到有事件；传 `0` 就看一眼立刻返回；传 `1000` 就是最多等 1000 毫秒，没事件也返回。

**和项目的关联**：项目传 `1000`（1 秒）。这样空闲时每秒醒来一次，可以驱动时间轮 tick。繁忙时被事件唤醒也能处理，同时用单调时钟判断是否真过了一秒才 tick。

```c
int n = epoll_wait(epfd, events, MAX_EVENTS, 1000);  // 最多等 1 秒
```

## 五、Reactor 模式拷打

### Q10：什么是 Reactor 模式？

**大白话**：Reactor 就像一个"总调度台"。它不亲自干活，只负责盯着所有人谁有事了，然后把任务分给空闲的工人。比起"来一个客招一个服务员"（每连接一线程），Reactor 用固定团队轮流转，效率高得多。

**专业术语**：Reactor 是一种事件驱动架构模式，核心组件：
1. **Event Demultiplexer（事件分发器）**：底层用 `epoll`/`select`，阻塞等待事件就绪
2. **Reactor（事件循环）**：主线程循环调用 `epoll_wait`，将就绪事件分发给对应的 Handler
3. **EventHandler（事件处理器）**：处理具体的 I/O 逻辑

```
Reactor 基本流程：
  while (true) {
      events = epoll_wait();           // 等待事件就绪
      for (event in events) {
          if (event.fd == listen_fd)
              accept_and_register();   // 新连接
          else
              dispatch_to_handler();   // 分发给处理器
      }
  }
```

---

### Q11：单 Reactor 和主从 Reactor 有什么区别？

**大白话**：
- **单 Reactor**：一个前台经理管所有事，既负责迎接新客人（accept），也负责给老客人分派服务员。经理太忙可能成为瓶颈。
- **主从 Reactor**：主经理只负责迎接新客人（accept），然后把客人分给若干副经理，副经理负责盯各自负责的客人的读写事件。分担了压力。

**专业术语**：
- **单 Reactor + 线程池**（本项目）：主线程一个 epoll，accept 和事件分发都在主线程，I/O 处理交给线程池。简单有效，主线程可能成为瓶颈（但实际压测 5 万 QPS 还没到瓶颈）。
- **主从 Reactor（Multi-Reactor）**：Main Reactor 只处理 accept，Sub Reactor 各自有一个 epoll 处理分配到的连接的读写事件。nginx/Netty 默认用此模式。

**面试加分话术**："我当前是单 Reactor + 线程池，在 5 万 QPS 下主线程还没成为瓶颈。如果要支持更高并发，可以演进为主从 Reactor——Main Reactor 只做 accept，Sub Reactor 各自管理一部分连接的事件分发，避免单线程 epoll_wait 成为瓶颈。这是 nginx 和 Netty 的做法。"

---

### Q12：Proactor 和 Reactor 的区别？

**大白话**：
- **Reactor**："有客人来了，你去接客"——通知你可以干了，你自己干。
- **Proactor**："我已经帮你把客人的需求处理好了，结果在这儿"——操作系统帮你干了，通知你结果。

**专业术语**：
- **Reactor**：同步非阻塞。epoll 通知"可读/可写"，应用自己执行 `recv`/`send`。
- **Proactor**：异步非阻塞。应用发起 `aio_read` 请求后立刻返回，内核完成 I/O 后通知应用。Linux 的 `io_uring` 是新一代异步 I/O 框架，比传统 `aio` 更高效。

---

## 六、线程池拷打

### Q13：线程池的核心原理是什么？

**大白话**：线程池就像一家餐厅养了一支固定的服务员团队。不来客人时服务员休息（等条件变量），来客人了经理把任务交给空闲服务员（条件变量唤醒），服务员干完回来继续休息。客人再多也是这 N 个服务员轮流转，绝不现场招人。

**专业术语**：线程池是**生产者-消费者模型**的实现：
- **生产者**（主线程）：产生任务，加锁追加到任务队列尾部，signal 唤醒一个消费者
- **消费者**（工作线程）：加锁检查队列，空则 `cond_wait` 阻塞，非空则取任务，解锁后执行

```
┌─────────┐      ┌──────────────────┐      ┌─────────────┐
│  生产者  │ →→→  │  任务队列（链表）  │ ←←←  │   消费者xN   │
│ (主线程) │ lock  │  head → ... → tail │ lock │ (工作线程)  │
└─────────┘      └──────────────────┘      └─────────────┘
                 mutex + cond
```

---

### Q14：为什么用线程池而不是每连接一线程？

**大白话**：每来一个客人就招一个全职服务员（v1 的做法），听起来很周到，但——
- 招人有开销（`pthread_create` 要分配栈、内核数据结构）
- 辞人有开销（线程销毁要回收资源）
- 200 个服务员挤在一起抢厨房（CPU 上下文切换），互相等

固定团队就没这些问题：人是一开始招好的，不用反复招辞；人少不挤，效率高。

**专业术语**：

| 维度 | 每连接一线程（v1） | 线程池（v2） |
|------|-------------------|-------------|
| 线程创建/销毁 | 每个连接都要 create + detach | 只在初始化时创建 N 个 |
| 资源消耗 | 200 并发=200 个线程=200 个栈（每栈 8MB） | 4 个线程=4 个栈 |
| 上下文切换 | 200 个线程竞争 CPU，调度抖动大 | 4 个线程稳定调度 |
| 延迟稳定性 | 标准差 109.7ms | 标准差 2.8ms |
| QPS | 5,897 | 21,568 |

---

### Q15：线程池的任务队列为什么用链表而不是数组/环形缓冲区？

**大白话**：用链表的好处是"不限人数"——任务再多都能排上队（直到内存耗尽）。数组有固定大小，满了就得拒绝任务或等空位。对于 HTTP 服务器来说，突发流量时任务可能瞬间涌入，链表不会丢任务。

**专业术语**：无界链表队列 vs 有界环形缓冲区：
- **无界链表**：动态分配节点，不会因队列满而拒绝任务。缺点是内存不受控，极端情况可能 OOM。适合请求量波动大的场景。
- **有界环形缓冲区**：固定大小，满了则阻塞生产者或丢弃。适合请求量可控的场景。

项目选择无界链表，因为 HTTP 服务器在突发流量时不希望拒绝请求。

---

### Q16：条件变量为什么必须配合互斥锁使用？

**大白话**：条件变量就像一个"等通知"的门铃。如果不用锁保护检查和等待的过程，可能产生这样的竞态：

1. 工作线程检查队列：空的
2. 主线程放入任务，按门铃
3. 工作线程还没进入等待状态，门铃白按了
4. 工作线程进入等待，永远等不到通知（因为通知已经发过了）

加锁后，检查→等待是一个原子操作，主线程放任务→按门铃也得先拿锁，不会插进来。

**专业术语**：`pthread_cond_wait` 内部会原子地"释放互斥锁 + 进入等待"（unavoidable TOCTOU race condition prevention）。如果不加锁，检查条件（`head == NULL`）和进入等待之间存在窗口：生产者可能在这个窗口内 signal，导致消费者永久阻塞（lost wakeup）。这也是为什么 `pthread_cond_wait` 的典型用法是：

```c
pthread_mutex_lock(&lock);
while (condition_not_met)         // 用 while 不用 if，防止虚假唤醒
    pthread_cond_wait(&cond, &lock);
// 执行逻辑
pthread_mutex_unlock(&lock);
```

---

### Q17：为什么条件变量用 while 循环检查而不是 if？

**大白话**：防止"假醒"。操作系统有可能在没有 signal 的情况下把你叫醒（虚假唤醒），用 if 的话你醒了就直接往下跑了，用 while 的话醒了还得再检查一次条件是不是真的满足了。

**专业术语**：**Spurious wakeup（虚假唤醒）**——POSIX 标准允许 `pthread_cond_wait` 在没有被 signal/broadcast 的情况下返回。因此必须在 `while` 循环中重新检查条件，而不是用 `if` 一次性判断。这是 POSIX 标准明确要求的（IEEE Std 1003.1）。

项目代码：
```c
while (pool->head == NULL && !pool->shutdown) {
    pthread_cond_wait(&pool->notify, &pool->lock);  // 虚假唤醒时 while 重新检查
}
```

## 七、HTTP 协议拷打

### Q18：HTTP 请求的格式是什么？

**大白话**：HTTP 请求就像一封信——

```
请求行：     GET /index.html HTTP/1.1\r\n        ← 方法 路径 协议版本
请求头：     Host: www.example.com\r\n             ← 键值对，一行一个
             Connection: keep-alive\r\n
             User-Agent: Mozilla/5.0\r\n
空行：       \r\n                                 ← 标志请求头结束
请求体：     （GET 请求通常没有 body）
```

**和项目的关联**：解析器需要找到 `\r\n\r\n`（空行）才能确认请求头完整收全。如果只收到一部分（半包），就等剩余数据到达再解析。

---

### Q19：什么是 HTTP 半包/粘包？怎么处理的？

**大白话**：
- **半包**：一个请求分两次到达。第一次 recv 只收到 `GET /index.ht`，第二次才收到 `ml HTTP/1.1\r\n...`。如果你只 recv 一次就解析，会解析失败。
- **粘包**：多个请求一次到达。一次 recv 收到 `GET /a HTTP/1.1\r\n\r\nGET /b HTTP/1.1\r\n\r\n`，两个请求粘在一起了。

**处理方法**：
- 半包：把已收数据保存在 `rbuf` 里，调用 `http_parse` 判断是否完整（找 `\r\n\r\n`），不完整就 `rearm_read` 等剩余数据。
- 粘包：循环解析，处理完第一个请求后用 `memmove` 把剩余数据前移，继续解析第二个请求。

**专业术语**：HTTP 协议本身是基于文本、以 `\r\n\r\n` 作为消息边界的（请求头部分）。TCP 是字节流协议，不保证一次 `recv` 对应一个完整的 HTTP 请求。项目使用**增量式解析器**，核心思想是状态机——每次收到数据喂给解析器，解析器返回三种状态：`PARSE_INCOMPLETE`（等待更多数据）、`PARSE_COMPLETE`（解析完成）、`PARSE_ERROR`（格式错误）。

---

### Q20：HTTP pipelining 是什么？

**大白话**：pipelining 就像连发请求——客户端不等第一个请求的响应回来，连续发三个请求过去。服务器要按顺序依次响应。一次 `recv` 可能同时收到多个完整请求。

**专业术语**：HTTP/1.1 pipelining 允许客户端在同一个 TCP 连接上连续发送多个请求而不必等待响应。服务器必须按请求顺序返回响应。HTTP/2 用多路复用（multiplexing）取代了 pipelining。

**和项目的关联**：`conn_worker` 中用 `for(;;)` 循环处理缓冲区中所有完整请求，每处理完一个用 `finish_response` 中的 `memmove` 移除已消费的请求头字节，继续解析剩余部分。

---

### Q21：Keep-Alive 是什么？HTTP/1.0 和 HTTP/1.1 有什么区别？

**大白话**：
- HTTP/1.0：默认"吃完就走"（短连接）。每次请求都要 TCP 握手+挥手，开销大。
- HTTP/1.1：默认"吃完先坐着"（Keep-Alive 长连接）。15 秒内还有事就继续用这条连接，省掉反复握手。

**专业术语**：
- HTTP/1.0 默认 `Connection: close`，每个请求独立建立 TCP 连接。
- HTTP/1.1 默认持久连接（RFC 7230），`Connection: keep-alive` 是默认行为，可用 `Connection: close` 显式关闭。
- Keep-Alive 省去了 TCP 三次握手和四次挥手的 RTT 开销，大幅提升 QPS。

**和项目的关联**：解析器判断 HTTP 版本，`HTTP/1.1` 默认 `keep_alive=1`，然后检查 `Connection` 头是否覆盖。响应头返回 `Connection: keep-alive` 或 `close`。QPS 从 21,568（短连接）→ 50,141（长连接）。

---

### Q22：HEAD 方法是什么？

**大白话**：HEAD 就是"我只看信封不拆信"。服务器只返回响应头（状态行 + Content-Type + Content-Length 等），不返回文件内容。常用于客户端检查文件是否存在、有多大、有没有更新。

**和项目的关联**：`build_response` 中检查 `is_head = (strcmp(req->method, "HEAD") == 0)`，如果是 HEAD 则关闭文件 fd、不发送 body，但 Content-Length 仍然是文件大小。

---

## 八、非阻塞 I/O 与 EAGAIN 拷打

### Q23：什么是非阻塞 I/O？和阻塞 I/O 有什么区别？

**大白话**：
- **阻塞 I/O**：你去快递站取包裹，包裹没到你就站那儿等，一直等到包裹来。期间什么都干不了。
- **非阻塞 I/O**：你问一句"包裹到了吗？"，没到就立刻告诉你"没到"，你可以去干别的，过一会儿再问。

**专业术语**：
- **阻塞 I/O（Blocking I/O）**：系统调用（recv/send）在数据未就绪/缓冲区满时将调用线程挂起，直到操作完成才返回。
- **非阻塞 I/O（Non-blocking I/O）**：设 `O_NONBLOCK` 后，系统调用在操作无法立即完成时返回 `-1` 且 `errno=EAGAIN/EWOULDBLOCK`，线程不被挂起。

**和项目的关联**：所有 socket 都设了 `SOCK_NONBLOCK`。工作线程 `recv` 到 EAGAIN 就不再等，直接去处理已有数据。`send` 遇到 EAGAIN 就保存发送现场、等 EPOLLOUT 续传。

---

### Q24：EAGAIN、EWOULDBLOCK、EINTR 分别是什么？

**大白话**：
- `EAGAIN` / `EWOULDBLOCK`："现在忙不过来，等会儿再来"。非阻塞操作没法立即完成时返回。两者在 Linux 上是同一个值。
- `EINTR`："你刚做到一半被领导叫走了"（信号中断），操作被信号打断，重新做一次就行。

**专业术语**：

| errno | 含义 | 正确处理 |
|-------|------|---------|
| `EAGAIN`/`EWOULDBLOCK` | 非阻塞 fd 暂时不可读/不可写 | 读：停止读取，等下次 EPOLLIN；写：保存进度，等 EPOLLOUT |
| `EINTR` | 系统调用被信号中断 | 直接重试（continue） |
| `ECONNRESET` | 对端发送了 RST | 连接已被重置，关闭连接 |

**和项目的关联**（flush_response 中的处理）：
```c
if (n < 0 && errno == EINTR)   continue;    // 信号中断，重试
if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK))
    return 1;                              // 缓冲满，等 EPOLLOUT
return -1;                                 // 其他错误，关闭连接
```

---

### Q25：send 返回的值比要求发送的少（短写/short write）怎么办？

**大白话**：你让快递员送 100 个包裹，他说"我这趟只能带 60 个，剩下的下次送"。你不能说"没送完就是失败"，得记住已送了 60 个，下次从第 61 个开始送。

**专业术语**：**Short write（短写）**——`send()` 的返回值可能小于请求的字节数 `len`，这在中大型数据发送或发送缓冲区较小时很常见。正确做法是循环发送，用偏移量记录已发送量。

**和项目的关联**：
```c
while (ctx->headsent < ctx->headlen) {
    ssize_t n = send(ctx->fd, ctx->headbuf + ctx->headsent, ...);
    if (n > 0) {
        ctx->headsent += n;  // 记录已发送量，循环继续
        continue;
    }
    // EAGAIN → 存现场，等 EPOLLOUT；EINTR → 重试
}
```

## 九、sendfile 零拷贝拷打

### Q26：sendfile 相比 read + write 有什么优势？

**大白话**：
- **read + write**：文件数据从仓库（磁盘）→搬到你办公室（用户态缓冲区）→再搬到快递车（socket 缓冲区）。搬了两次，你办公室只是中转站，数据停留了但没做任何加工。
- **sendfile**：文件数据直接从仓库搬到快递车，不经过你办公室。少搬一次，省时省力。

**专业术语**：

```
传统 read + write（4 次上下文切换 + 4 次拷贝）:
  用户态 ──read()──→ 内核态（磁盘→内核缓冲区→用户缓冲区）──write()──→ 内核态（用户缓冲区→socket缓冲区→网卡）
  2 次系统调用 + 2 次 CPU 拷贝 + 2 次 DMA 拷贝

sendfile（2 次上下文切换 + 3 次拷贝）:
  用户态 ──sendfile()──→ 内核态（磁盘→内核缓冲区→socket缓冲区→网卡）
  1 次系统调用 + 0 次 CPU 拷贝（数据不经过用户态）+ 2 次 DMA 拷贝
  Linux 2.4+ 进一步优化：SG-DMA，数据直接从内核缓冲区到网卡，0 次 CPU 拷贝
```

| 维度 | read + write | sendfile |
|------|-------------|----------|
| 系统调用 | 2 次 | 1 次 |
| 上下文切换 | 4 次 | 2 次（甚至 0 次，SG-DMA） |
| CPU 拷贝 | 2 次 | 0 次 |
| 用户态缓冲区 | 需要 | 不需要 |
| 适用场景 | 需要修改数据 | 纯传输不修改 |

---

### Q27：sendfile 的参数为什么要传偏移量？

**大白话**：sendfile 的偏移量是一个"书签"——记录文件读到哪了。如果发送中断了（比如缓冲区满返回 EAGAIN），下次调用时从这个书签继续，不用从头开始发。这就是断点续传。

**专业术语**：`sendfile(out_fd, in_fd, &offset, count)` 的 `offset` 是输入输出参数：传入起始偏移，返回发送后的新偏移。传 `NULL` 表示从当前文件位置开始。项目用显式偏移 `off = ctx->filesent`，因为 EAGAIN 后需要从上次中断处续传。

**和项目的关联**：
```c
off_t off = ctx->filesent;                                    // 断点
ssize_t n = sendfile(ctx->fd, ctx->filefd, &off,              // 从断点继续
                     (size_t)(ctx->filetotal - ctx->filesent));
if (n > 0) {
    ctx->filesent += n;                                       // 更新断点
}
```

---

### Q28：sendfile 只能用于什么场景？

**专业术语**：`sendfile()` 要求 `in_fd` 必须支持 `mmap`（即普通文件），`out_fd` 在 Linux 2.6.33 之前必须是 socket，之后可以是任意文件。不能用于管道（pipe）或非文件 fd 作为输入。

**和项目的关联**：项目的 `in_fd` 是 `open()` 返回的文件 fd，`out_fd` 是客户端 socket fd，符合要求。

---

## 十、Keep-Alive 长连接拷打

### Q29：Keep-Alive 怎么提升性能的？省了什么？

**大白话**：省的就是"反复开门关门"的时间。每次 TCP 连接要 3 次握手（1.5 个 RTT）+ 4 次挥手（约 2 个 RTT）。一个网页往往要请求 HTML + CSS + JS + 10 张图片 = 十几个请求。短连接要开关十几次门，长连接只开一次门，全程用同一扇门。

**专业术语**：Keep-Alive 的收益：
1. 省去后续请求的 TCP 握手/挥手 RTT（约 1.5 + 2 = 3.5 RTT/请求）
2. 避免 TCP 慢启动（slow start）每次从 cwnd=1 重新开始
3. 减少系统调用（accept/close）和文件描述符消耗

**和项目的关联**：QPS 从 21,568（短连接）→ 50,141（长连接），提升 2.3 倍，P99 从 61ms → 9.66ms。

---

### Q30：长连接怎么管理？客户端一直不发请求怎么办？

**大白话**：客人吃完坐着一动不动，座位就浪费了。所以要装一个"15 分钟不动就请走"的计时器。项目设的是 15 秒，超过 15 秒没新请求就自动关闭连接。

**专业术语**：Keep-Alive 连接需要**空闲超时回收**机制，否则空闲连接会耗尽文件描述符。项目用时间轮定时器，15 秒无数据则回调 `close(fd)` + `free(ctx)`。

---

## 十一、时间轮定时器拷打

### Q31：什么是时间轮？为什么不用链表 + 遍历？

**大白话**：时间轮就像一个钟面，有 60 个刻度（槽位）。指针每秒走一格。要设 15 秒后超时，就把任务挂在"当前刻度+15"的那个格子上。指针走到那格时检查所有任务。比"把所有定时器排成一列，每次从头到尾扫一遍"高效得多——时间轮是 O(1) 添加、O(1) 删除，只需要在指针扫到的格子处理到期任务。

**专业术语**：单轮时间轮（Single-level Timing Wheel）：
- **创建**：分配 `slot_count` 个槽，每槽一个链表头
- **添加**（O(1)）：计算 `rotation = timeout / slots`，`slot = (cur + timeout) % slots`，头插到该槽链表
- **tick**（O(当前槽链表长度)）：检查当前槽所有节点，`rotation > 0` 则减一留下，`rotation == 0` 则到期触发回调
- **删除**（O(n)）：遍历槽位链表摘除

对比其他定时器方案：

| 方案 | 添加 | 删除 | tick | 适用场景 |
|------|------|------|------|---------|
| 链表遍历 | O(1) | O(n) | O(n) | 定时器少 |
| 时间轮 | O(1) | O(n)* | O(当前槽) | 大量相同精度定时器 |
| 最小堆 | O(log n) | O(log n) | O(1)** | 任意精度 |
| 跳表 | O(log n) | O(log n) | O(1) | 任意精度 |

*项目的删除遍历所有槽，实际可以优化为 O(1) 用 fd → node 哈希表
**最小堆的 tick 只看堆顶是否到期

---

### Q32：时间轮的 rotation 是什么意思？

**大白话**：时间轮有 60 格，一圈就是 60 秒。如果你要设 75 秒后超时，75 = 60 + 15，所以要转 1 圈再多走 15 格。`rotation = 1`，`slot = cur + 15`。指针走到那格时，发现 rotation=1，就减成 0 让它再留一圈；下一圈指针再走到那格，rotation=0，就到期了。

**专业术语**：`rotation` 表示定时器需要等待时间轮转过的整圈数。`tick` 时只触发 `rotation == 0` 的节点，`rotation > 0` 的节点减一后留在原槽等待下一圈。

---

### Q33：tick 频率怎么控制？为什么不能每次 epoll_wait 都 tick？

**大白话**：时间轮设计是"每秒滴答一次"。但如果每次 epoll_wait 返回都滴答一次，压测时 epoll_wait 每秒被唤醒上万次，钟面就疯狂飞转——15 秒的闹钟几毫秒就响了，正在吃饭的客人被轰走了。

**修复**：不能按"干了多少轮"来计时，要用真实时钟（单调时钟）判断是不是真过了一秒。

**专业术语**：使用 `CLOCK_MONOTONIC`（单调时钟，不受 NTP 调整影响）限制 tick 节拍：

```c
struct timespec last_tick;
clock_gettime(CLOCK_MONOTONIC, &last_tick);
// 主循环中：
struct timespec now;
clock_gettime(CLOCK_MONOTONIC, &now);
long elapsed_ms = (now.tv_sec - last_tick.tv_sec) * 1000
                + (now.tv_nsec - last_tick.tv_nsec) / 1000000;
if (elapsed_ms >= 1000) {           // 真正过了 1 秒才 tick
    timer_wheel_tick(timer);
    last_tick = now;
}
```

---

### Q34：为什么用 CLOCK_MONOTONIC 不用 time()？

**大白话**：`time()` 返回的是墙上的钟（挂钟时间），如果有人手动调了钟（比如 NTP 校时、夏令时切换），钟可能往前跳或往后跳，你的定时器就全乱了。`CLOCK_MONOTONIC` 是"从系统开机开始一直在走的秒表"，永远不会往回跳，只增不减。

**专业术语**：
- `time()` / `CLOCK_REALTIME`：挂钟时间，受 NTP 调整和用户手动改时间影响，可能跳跃（向前或向后）。
- `CLOCK_MONOTONIC`：单调递增时钟，不受系统时间修改影响，适合测量时间间隔和驱动定时器。

## 十二、线程安全与竞态条件拷打

### Q35：什么是竞态条件（Race Condition）？

**大白话**：两个线程同时操作同一个东西，谁先谁后不确定，结果取决于"运气"。就像两个人同时抢一张票，如果系统没有锁保护，可能出现"两个人都抢到了"或"票数变负数"的bug。

**专业术语**：竞态条件是指多个线程并发访问共享资源，且至少一个线程进行写操作，且访问顺序未加同步控制时，程序行为依赖于线程调度的不确定时序。解决方法是互斥（mutex）、原子操作或避免共享。

---

### Q36：项目中最严重的竞态是什么？怎么解决的？

**大白话**：服务员正在给一桌客人上菜，翻台计时器响了，以为这桌客人走了，冲过去把桌子收了（fd 关了、内存释放了）。服务员端着菜回来一看：桌子没了！一伸手抓了个空（操作已释放的内存），程序崩溃。这就是 use-after-free。

**解决方案**：在经理把任务交给服务员的那一刻，就先把这桌的计时器摘掉。服务员服务期间，计时器绝对不可能响。从流程上消除竞态窗口。

**专业术语**：

**问题**：`conn_worker`（工作线程）和 `on_conn_timeout`（定时器回调）可能并发操作同一个 `conn_ctx_t`。投递任务后、工作线程执行前，时间轮可能 tick 到期，回调 `free(ctx)`。工作线程随后操作已释放的 ctx → **use-after-free** → 段错误。

**修复**：将定时器摘除时机从"工作线程开始处理时"提前到"主线程投递任务前"：

```c
// 主线程事件分发处
timer_wheel_remove(timer, ctx->fd);     // ① 先摘定时器
threadpool_add(pool, conn_worker, ctx);  // ② 再投递
```

工作线程独占连接期间，定时器不存在，竞态窗口从设计上消除。

---

### Q37：rearm 顺序为什么必须是"先定时器后 epoll"？

**大白话**：服务员忙完一桌，要做两件事：① 重新举手叫号（epoll_ctl MOD）② 挂上新计时器。如果先举手再挂计时器，可能出现：经理看到客人举手了，冲过去摘计时器——可新计时器还没挂上去呢，摘了个空气。之后服务员挂上计时器 A，下次又挂一个计时器 B，一桌挂了两个表。15 秒后 A 表响了，把正被别人服务的连接关了。

**修复**：调换顺序——先挂计时器、再举手叫号。保证"经理可能看到客人举手"的那一刻，计时器一定已经挂好了。

**专业术语**：EPOLLONESHOT 的 rearm 顺序约束——必须先 `timer_wheel_add`（确保定时器存在），再 `epoll_ctl(MOD)`（武装 epoll）。否则在两步之间，主线程可能 `epoll_wait` 返回新事件并执行 `timer_wheel_remove`，但此时定时器尚未注册 → remove 摘空 → 同一 fd 残留多个定时器节点 → 后续到期回调 use-after-free。

额外防线：`timer_wheel_add` 内部持锁遍历所有槽，先摘除同 fd 的旧节点，从数据结构层面保证"同一 fd 至多一个定时器节点"的不变式。

---

### Q38：volatile 和 sig_atomic_t 是什么？为什么要用？

**大白话**：`volatile` 告诉编译器"这个变量可能被其他线程/信号处理函数修改，不要优化到寄存器里，每次都从内存读"。`sig_atomic_t` 保证对这个变量的读写是原子的（不会被信号打断到一半）。

**专业术语**：
- `volatile`：防止编译器将变量缓存到寄存器，确保每次访问都从内存读取。注意：C 语言的 `volatile` **不保证原子性和可见性**（与 Java 不同），只防编译器优化。
- `volatile sig_atomic_t`：POSIX 推荐的信号处理中安全使用的类型。信号处理函数中只能写这种类型的变量。

**和项目的关联**：
```c
static volatile sig_atomic_t g_stop = 0;  // 信号处理函数中修改
static void on_signal(int sig) {
    g_stop = 1;                            // 原子地设置停止标志
}
// 主循环
while (!g_stop) { ... }                     // 每次都从内存读取
```

## 十三、TCP 协议栈拷打（Nagle/Delayed ACK）

### Q39：Nagle 算法是什么？

**大白话**：Nagle 算法是 TCP 的"省快递费"策略——如果你要发的小包裹不足一车（MSS），就先攒着，等凑够一车再发，或者等上一个包裹收到回执（ACK）再发。目的是减少网络上的小包数量。

**专业术语**：Nagle 算法（RFC 896）——当 TCP 发送缓冲区中有未确认的小段数据时，不发送新的小段（< MSS），等待积累到 MSS 或收到 ACK 后再发送。减少网络中的小包数量，提高带宽利用率。

---

### Q40：Delayed ACK 是什么？

**大白话**：Delayed ACK 是"收到包裹不急着说收到了"——收到数据后不立刻发 ACK 确认，最多等 40 毫秒，看有没有数据要一起带回去（TCP 的 ACK 可以搭便车 piggyback）。省 ACK 包的数量。

**专业术语**：Delayed ACK（RFC 1122）——TCP 接收方收到数据后不立即发送 ACK，而是等待最多 40ms（典型值），期望有数据要发送时将 ACK 捎带在响应中。

---

### Q41：Nagle × Delayed ACK 导致 40ms 延迟是什么？

**大白话**：这是两个"省"的算法互相等造成的死锁——
- 服务器发了小包（响应头 + 文件尾包），Nagle 说"太小了，等收到 ACK 再发"
- 客户端收到小包，Delayed ACK 说"不急，等 40ms 再说 ACK"
- 服务器等客户端的 ACK → 客户端 40ms 才发 ACK → 每个请求白等 40ms

短连接反而没这个问题，因为关闭连接时的 FIN 会顺便把数据 flush 出去。

**修复**：设 `TCP_NODELAY` 禁用 Nagle——"有数据立刻发，别攒着"。这是 Nginx 等专业 HTTP 服务器的默认做法。

**专业术语**：Nagle 与 Delayed ACK 的交互死锁：
1. 发送方有小数据待发（< MSS），Nagle 阻止发送，等待 ACK
2. 接收方收到数据，Delayed ACK 延迟 40ms 发确认
3. 发送方等待 ACK 到达才能发下一个小段 → 固定 40ms 延迟

```c
int nodelay = 1;
setsockopt(cfd, IPPROTO_TCP, TCP_NODELAY, &nodelay, sizeof(nodelay));
```

**效果**：Keep-Alive 平均延迟 43.59ms → 3.63ms，QPS 4,540 → 50,141。

---

### Q42：什么时候该开 Nagle 什么时候该关？

**大白话**：
- **关 Nagle（TCP_NODELAY）**：交互式应用（HTTP、SSH、游戏），要的是"有数据立刻发，延迟低"。
- **开 Nagle（默认）**：大数据传输（文件下载），要的是"省带宽，少发小包"。

## 十四、安全防护拷打

### Q43：什么是目录遍历攻击？怎么防？

**大白话**：目录遍历就是"有人想通过 URL 偷看不该看的文件"。比如请求 `/../../../etc/passwd`，如果服务器不做检查，可能把系统密码文件返回给客户端。

**专业术语**：Path Traversal（路径遍历/CVE 常见类）——攻击者通过在 URL 中插入 `../` 序列，试图访问 Web 根目录之外的文件。

---

### Q44：为什么先 URL 解码再检查 `..`？

**大白话**：黑客可以不直接写 `..`，而是写 `%2e%2e`（URL 编码的 `..`）。如果你先检查 `..` 再解码，检查时看到的是 `%2e%2e` 不包含 `..`，放过了；解码后变成 `..`，但已经检查过了。所以必须先解码再检查。

**专业术语**：如果先安全检查再 URL 解码，攻击者可以用 `%2e%2e`、`%2E%2E`、`%2e%2e%2f` 等编码形式绕过 `..` 检测。正确顺序是**先解码再检查**：

```c
// 1. URL 解码
url_decode(req->path, sizeof(req->path), raw_path);   // %2e%2e → ..

// 2. 解码后检查
if (strstr(req->path, "..") != NULL)                  // 此时能检测到
    return PARSE_ERROR;
```

---

### Q45：除了目录遍历，还有什么安全措施？

| 措施 | 代码位置 | 说明 |
|------|---------|------|
| 请求头大小限制 | `READ_BUFFER_SIZE=65536` + `rlen >= sizeof(rbuf)` 检查 | 防止超大请求头耗尽内存 |
| 空闲连接超时 | 时间轮 15s 超时回收 | 防止慢速 DoS（Slowloris）耗尽 fd |
| SIGPIPE 忽略 | `signal(SIGPIPE, SIG_IGN)` + `MSG_NOSIGNAL` | 防止对端断开导致进程崩溃 |
| 仅支持 GET/HEAD | `build_response` 方法检查 | 拒绝 POST/PUT/DELETE |
| SO_REUSEADDR | `setsockopt(SO_REUSEADDR)` | 端口复用，不涉及安全但涉及可用性 |

## 十五、异步日志拷打

### Q46：为什么要做异步日志？同步日志有什么问题？

**大白话**：同步日志就像服务员一边上菜一边写流水账——写账本要时间，菜就凉了（阻塞 I/O 影响请求处理速度）。异步日志就是服务员喊一嗓子"这桌 3 号菜"然后继续上菜，有个专门的记账员后台慢慢写。

**专业术语**：同步日志（sync logging）的 `write()`/`fprintf()` 是阻塞系统调用，高并发下磁盘 I/O 延迟直接拖慢工作线程。异步日志（async logging）将日志消息入队（内存操作，O(1)），后台线程批量从队列取出落盘，I/O 不阻塞业务线程。这也是 muduo 日志库、Java Log4j AsyncAppender 的设计思路。

---

### Q47：异步日志的生产者-消费者模型怎么实现的？

**大白话**：
- 生产者（工作线程）：格式化日志 → 分配节点 → strdup 消息 → 加锁入队 → signal 唤醒 → 解锁
- 消费者（日志线程）：加锁 → 队列空就 cond_wait → 被唤醒后取出整条队列 → 解锁 → 锁外批量 fputs

**专业术语**：
```
工作线程（生产者）                     日志线程（消费者）
    │                                      │
    ├─ snprintf 格式化                     │
    ├─ malloc(log_node_t)                  │
    ├─ strdup(msg)                         │
    ├─ lock(&g_log.lock)                   │
    ├─ tail->next = node                   │
    ├─ cond_signal(&g_log.cond)            │
    ├─ unlock                              │
    │                                      ├─ lock(&g_log.lock)
    │                                      ├─ while(head==NULL && !shutdown)
    │                                      │     cond_wait(&g_log.cond, &g_log.lock)
    │                                      ├─ batch = head; head=tail=NULL
    │                                      ├─ unlock
    │                                      ├─ while(batch) { fputs; free }
    │                                      └─ fflush(fp)
```

---

### Q48：为什么用批量写入而不是一条一条写？

**大白话**：每写一条日志就调一次 `fputs` + `fflush`，1000 条日志就是 1000 次系统调用。批量取出 1000 条一次写完，只要 1 次 flush，大大减少系统调用次数。

**专业术语**：批量写入（batching / group commit）减少系统调用次数和磁盘寻道次数。一次 `fflush` 刷盘比多次 `fflush` 效率高得多，是数据库 WAL（Write-Ahead Log）和消息队列的常见优化。

---

## 十六、信号与优雅退出拷打

### Q49：怎么实现优雅退出？

**大白话**：用户按 Ctrl+C 时，不是直接杀进程（可能正在给客人上菜，杀掉了菜就没了），而是设个"打烊了"的标志，主循环看到标志就不再接新客，等当前正在服务的客人服务完再关门。

**专业术语**：
```c
static volatile sig_atomic_t g_stop = 0;    // 原子停止标志

static void on_signal(int sig) {
    g_stop = 1;                               // 信号处理函数只设标志
}

// 主循环
while (!g_stop) { ... }                       // 检查标志

// 退出后优雅清理
close(lfd);                // 不再接受新连接
threadpool_destroy(pool);  // 等队列排空、join 所有工作线程
timer_wheel_destroy(timer); // 释放所有定时器
close(epfd);
log_shutdown();             // 唤醒日志线程刷盘、join
```

信号处理函数中只做最少的事（只设标志），不做不可重入的操作（如 malloc/printf），因为信号处理函数可能打断主线程正在执行这些操作。

---

### Q50：为什么忽略 SIGPIPE？

**大白话**：如果你给客人上菜时客人已经走了（对端断开），操作系统会给你发一个 SIGPIPE 信号，默认行为是杀掉你的进程。这太暴力了——一个客人走了你整个餐厅就关门了？所以要把 SIGPIPE 设为忽略，然后 `send` 会返回 `-1` 报错，你检查错误自己处理就行。

**专业术语**：当向已关闭（对端发送 RST/FIN）的 socket 写数据时，内核向进程发送 SIGPIPE，默认终止进程。HTTP 服务器必须忽略 SIGPIPE（`signal(SIGPIPE, SIG_IGN)`），并在 `send()` 时使用 `MSG_NOSIGNAL` 标志阻止该次调用产生 SIGPIPE，改为返回 `-1` + `errno=EPIPE`。

## 十七、Linux 系统编程拷打

### Q51：文件描述符（fd）是什么？

**大白话**：fd 就是一个"编号"，操作系统给你发的"存物牌"。你打开一个文件、建一个 socket，操作系统给你一个数字（0/1/2 已被 stdin/stdout/stderr 占了，从 3 开始）。你拿着这个数字去操作，操作系统就知道你要操作哪个东西。

**专业术语**：文件描述符（File Descriptor）是非负整数，是用户空间引用内核中文件表项的索引。Linux 中一切皆文件，socket、普通文件、管道、epoll 实例都是 fd。每个进程默认最多 1024 个 fd（`ulimit -n` 可查）。

---

### Q52：epoll 内部是怎么实现的？

**大白话**：epoll 内部有两个东西——一棵红黑树和一个就绪列表。你 `epoll_ctl(ADD)` 时把 fd 存到红黑树里，同时内核给这个 fd 注册一个回调。当网卡收到数据，内核通过回调把这个 fd 放到就绪列表里。你 `epoll_wait` 时直接从就绪列表拿，不用遍历红黑树。

**专业术语**：
- `epoll_create1()`：创建 `struct eventpoll`，包含一棵红黑树（rbr，存放注册的 fd）和一个双向链表（rdllist，就绪列表）
- `epoll_ctl(EPOLL_CTL_ADD)`：在红黑树中插入节点，并在内核中为该 fd 注册回调函数 `ep_poll_callback`
- 数据到达 → 网卡 DMA → 内核 skb → 回调触发 → 将节点加入 rdllist
- `epoll_wait()`：检查 rdllist，非空则拷贝到用户态 events 数组并返回；空则阻塞（或超时返回）

---

### Q53：accept4 的 backlog 参数是什么意思？

**大白话**：backlog 就是"候客区大小"。客人在门口排队等 accept，候客区满了新客人就被拒绝。设大一点能容纳更多排队的连接。

**专业术语**：`listen(fd, backlog)` 的 backlog 表示**已完成三次握手但未被 accept 的连接队列**长度。超过 backlog 的新连接会被内核拒绝（发 RST 或忽略 SYN）。Linux 中实际值 = `min(backlog, somaxconn)`，`somaxconn` 默认 4096（可配）。项目设 1024。

## 十八、C 语言与内存管理拷打

### Q54：malloc / calloc / free 的区别？

**大白话**：
- `malloc(100)`：找一块 100 字节的空间给你，里面可能是垃圾数据（上次用完没清的）
- `calloc(1, 100)`：找 100 字节给你，而且帮你清成全零
- `free(p)`：把空间还给系统

**和项目的关联**：`conn_ctx_t` 用 `calloc`（结构体字段需要清零初始化），`task_t` 用 `malloc`（后面会手动赋值每个字段），`log_node_t` 用 `malloc` + `strdup`。

### Q55：use-after-free 是什么？怎么排查？

**大白话**：你把房子卖了（free），但还留着钥匙（指针），还开门进去拿东西——房子已经不是你的了，里面可能住着别人，你一开门就出事了（段错误/数据错乱）。

**专业术语**：Use-After-Free（UAF）——访问已释放的内存。行为未定义（UB）：可能段错误、可能读到被其他分配覆盖的脏数据、可能被攻击者利用（UAF 是常见 CVE 类型）。排查工具：Valgrind、AddressSanitizer（ASan）。

**和项目的关联**：定时器回调 `free(ctx)` 后，工作线程继续操作 `ctx` 就是 UAF。通过时序约束（投递前摘定时器）从设计上消除。

---

### Q56：函数指针是什么？项目里哪里用到了？

**大白话**：函数指针就是"把函数当变量传"。就像你告诉快递公司"送到这个地址"（地址=函数指针），快递公司不需要知道送到那个地址后具体干什么，它只需要送到。

**和项目的关联**：
```c
// 线程池的任务函数指针
typedef void (*task_func)(void *);
int threadpool_add(threadpool_t *pool, void (*routine)(void *), void *arg);
//                                                    ^^^^^^^^^^^^^^^^^^ 函数指针

// 定时器回调函数指针
typedef void (*timer_callback)(int fd, void *arg);
int timer_wheel_add(..., timer_callback cb, void *arg);
//                           ^^^^^^^^^^^^^^^^^^ 函数指针

// 使用
threadpool_add(pool, conn_worker, ctx);   // conn_worker 就是函数指针
timer_wheel_add(timer, fd, 15, on_conn_timeout, ctx);  // on_conn_timeout 是函数指针
```

## 十九、压测与性能分析拷打

### Q57：wrk 压测工具怎么用？怎么读结果？

**大白话**：wrk 就是模拟一堆客人同时上门，看你的餐厅能扛住多少。重点看三个数：
1. **QPS（Requests/sec）**：每秒处理多少请求，越高越好
2. **Latency**：客人等了多久，越短越好。但要看标准差，不只是平均值
3. **Socket errors**：多少客人被搞砸了，必须是 0

**和项目的关联**：
```bash
wrk -t4 -c200 -d10s --latency http://127.0.0.1:8080/index.html
# -t4: 4 个线程发请求
# -c200: 200 个并发连接
# -d10s: 持续 10 秒
# --latency: 输出延迟分布
```

---

### Q58：为什么"QPS 高不一定健康"？

**大白话**：有一次压测出 18,407 QPS 的"好成绩"，但其实是连接被疯狂杀掉后客户端不停重连造成的假象——就像餐厅把客人赶走又重新迎客，流水很高但全是无效的。必须结合错误数和延迟一起看。

**专业术语**：高 QPS + 高 Socket errors 可能是"虚高"——连接被服务器异常关闭（RST），客户端重连重试推高了请求计数。健康指标必须同时满足：QPS 高 + Socket errors = 0 + 延迟标准差小。

---

### Q59：延迟标准差大说明什么？延迟集中在固定值说明什么？

**大白话**：
- **标准差远大于平均值、Max 达秒级**：说明延迟忽高忽低，是线程调度/锁竞争/资源争抢导致。v1 的标准差 109.7ms 就是这种情况。
- **标准差很小、平均值卡在固定值**：说明每次都在等同一个东西，是协议栈/锁的固定等待。延迟稳定在 43.59ms（标准差仅 3.1ms）指向 Nagle × Delayed ACK 的 40ms 固定等待。

**专业术语**：
- 高方差延迟 → 调度抖动（scheduling jitter），可能由线程上下文切换、锁争用引起
- 低方差但高延迟 → 固定等待（fixed wait），指向协议栈层（Nagle/Delayed ACK）或锁的自旋等待

## 二十、6 个真实踩坑场景（高频追问）

> 面试官最爱的追问方式："你在做这个项目时遇到什么困难？怎么解决的？"以下 6 个场景按面试常考顺序排列。

### 场景 1：EAGAIN 被误判为致命错误（QPS 3.47 → 547）

**面试话术**：
> "第一版压测时 QPS 只有 3.47，wrk 报了 27 万个 write 错误。排查发现是非阻塞 socket 的 send/sendfile 遇到 EAGAIN 时被我当成了发送失败直接关闭连接。EAGAIN 不是错误，是'缓冲区满了，等会再发'。我重构了发送逻辑：拆成 build_response（准备响应）和 flush_response（增量发送），发送现场保存在 conn_ctx 里，遇到 EAGAIN 就切到 CONN_WRITING 状态注册 EPOLLOUT，等可写事件后续传。修复后 QPS 到了 547。"

---

### 场景 2：定时器与工作线程的 use-after-free（段错误）

**面试话术**：
> "修复 EAGAIN 后出现段错误。排查发现是定时器回调和工作线程的竞态：投递任务后、工作线程处理前，时间轮可能 tick 到期，回调 free 了 ctx，工作线程操作已释放的内存。解决方案是把定时器摘除从工作线程提前到主线程投递任务前——timer_remove 先于 threadpool_add。从时序上消除了竞态窗口。"

---

### 场景 3：rearm 顺序导致双定时器节点（偶发段错误）

**面试话术**：
> "修复 UAF 后仍偶发崩溃。根因是 rearm 顺序：原来先 epoll_ctl MOD 再 timer_add，两步之间主线程可能 epoll_wait 返回新事件并 timer_remove，但新定时器还没加上，remove 摘了个空。之后同一 fd 残留两个定时器节点，旧的到期时回调 free 了正在被处理的 ctx。修复是统一为'先 timer_add 后 epoll_ctl MOD'，并在 timer_wheel_add 内部加了持锁去重。"

---

### 场景 4：时间轮飞转（9.5 万 read 错误 + 虚假 18K QPS）

**面试话术**：
> "这是最隐蔽的一个。修完前面的问题后还有 9.5 万 read 错误，还有一次跑出 18K QPS 的假象。根因是时间轮的 tick 写在 epoll_wait 返回后每次都执行——空闲时每秒 tick 1 次正常，但压测时 epoll_wait 每秒被唤醒上万次，时间轮每秒狂转上万格，15 秒的超时几毫秒就到期了，活跃连接被批量误杀。那个 18K QPS 是连接被杀后客户端不停重连的虚高。修复是用 CLOCK_MONOTONIC 限制每秒才 tick 一次。"

---

### 场景 5：Nagle × Delayed ACK 的 40ms 固定延迟

**面试话术**：
> "定时器修好后错误清零了，但 Keep-Alive 平均延迟稳定在 43.59ms，标准差才 3.1ms，而且比短连接还慢。延迟集中在固定值说明不是排队抖动而是协议栈固定等待。排查发现是 Nagle 算法和 Delayed ACK 的交互死锁：服务器发了小包被 Nagle 攒着等 ACK，客户端的 Delayed ACK 最多延迟 40ms，每请求白等 40ms。修复是 accept 后立即 setsockopt TCP_NODELAY 禁用 Nagle，延迟降到 3.63ms，QPS 从 4540 到 50141。"

---

### 场景 6：v1 每连接一线程的固有瓶颈

**面试话术**：
> "v1 版本每连接创建一个 detached 线程，100 并发下 QPS 只有 5897，标准差 109.7ms，最大延迟 1.67 秒，还有 11 次超时。根因是大量线程的创建销毁和上下文切换开销。这正是 v2 用固定线程池 + epoll 事件驱动解决的——线程数不随连接数增长，QPS 提升 3.7 倍，延迟标准差降到 2.8ms。"

## 二十一、项目对比与架构选型拷打

### Q60：你这个项目和 Nginx 比有什么差距？

**诚实回答话术**：

### Q61：为什么用 C 不用 C++/Go/Rust？

**话术**：
